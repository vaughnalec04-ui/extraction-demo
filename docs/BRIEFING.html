Meridian Claims Group: field extraction on the Gemini API

Partner Engineering Briefing

BLUF. The accuracy and cost requirements are met; the requirement that the system know when it is unsure is not. A single lite-class reader, gemini-3.5-flash-lite, reads 99.2% [97.0–99.8] of fields correctly at $0.0013 per document, and the lower bound of that interval sits exactly on the 97% target. Two lite-class readers run as a double-key pair reach 100% [98.4–100] on the 96.7% of fields on which they agree, at $0.0022 per document. On the same documents, the two systems differ on two field-instances (p = 0.50), so the effect this sample establishes is a coverage cost of 3.3 points rather than an accuracy gain. Self-reported confidence is nearly constant and cannot gate anything; disagreement between readers is the only usable signal, and its precision on 8 flags is 25% [7.1–59.1]. I recommend running this harness unchanged on about 500 real Meridian documents before choosing a configuration; the decision gates are in section 2.5. The one request to GDM is a calibrated confidence output for structured extraction (F-007).

Context

Meridian Claims Group is a composite partner profile built for this exercise. It receives about 40,000 scanned claims documents a month and needs six payment-critical fields extracted from each: the claim id, the policy number, the claimant, the provider, the date of service, and the total amount. Its requirements are 97% field accuracy, a cost under $0.02 per document, and a system that flags what it is unsure of rather than guessing, because a wrong payout costs far more than a review. I built a prototype extractor and an evaluation harness on a synthetic corpus of 80 documents. The labels were written first and each page was rendered from its label, so the failure distribution is my estimate of Meridian's rather than a measurement of it. Everything ran on the free API tier, which forced one design change (section 1.3) and produced most of section 3. All figures come from results/results.json in the repository (github.com/vaughnalec04-ui/extraction-demo), where meridian-evaluate reproduces them from the committed response cache without an API key; bracketed ranges are 95% Wilson intervals.

1. Architecture

1.1 Flow

The pipeline runs in five stages. Labels are authored first from a fixed seed. Pages are rendered from those labels in five strata, with scanner noise and JPEG loss on every page. The extractor sends each page to Gemini with a response schema and receives one nullable value and one confidence per field. Every raw response is written to a cache that is keyed on the model, the prompt version, the schema, and the image bytes, and the cache is committed to the repository. The harness scores the cache offline and never calls the API.

Extraction and scoring are separate programs. Because thresholds are chosen from cached responses, sweeps cost no calls, tuning is reproducible, and the demo replays offline with identical numbers. Both programs recompute the cache key when they read, so a regenerated page cannot be scored against an old response; that failure would produce plausible wrong numbers rather than an error, which is why it is checked and refused.

1.2 Configurations

  • primary_solo uses one reader, gemini-3.5-flash-lite, and abstains on low self-reported confidence.
  • verifier_solo uses the second reader, gemini-3.1-flash-lite, on its own under the same rule.
  • cascade lets the primary read first and sends the page to the verifier when the primary's confidence is low.
  • double_key runs both readers on every page and sends a field to review when their normalized values disagree. This automates the double-keying control that Meridian's processors already run with people.

2. Evaluation

2.1 Definitions

  • The unit of measurement is the field-instance, meaning one field on one document, because Meridian pays per field. Exact match and normalized match are both reported and are never merged.
  • There are three kinds of error, and they are never pooled: a wrong value is a wrong payout, a missed field is a rekey, and a hallucinated field is a payment on a page that is not a claim. Accuracy is never reported without coverage, and abstention precision uses the recorded counterfactual for each flag.
  • Calibration is measured in ten confidence bins with the expected calibration error, and the curve is flagged as degenerate when fewer than two bins hold enough predictions to estimate from. Every proportion carries a 95% Wilson interval.
  • Configurations are compared in pairs on the same documents, using McNemar's exact test on discordant instances and a bootstrap that resamples documents.
  • Reconciliation asks whether the itemization sums to the stated total. It is the adjudication step beneath the transcription, and it is where a processor loses money.

2.2 Protocol

The corpus holds 80 documents in five strata (24 clean, 16 ambiguous, 16 degraded, 16 incomplete, and 8 out-of-distribution), split into 40 tune and 40 test documents before the first API call. Thresholds were swept on the tune split only, and the test split was scored once.

The cascade is not shown separately, because tuning set its escalation threshold to zero and on the test split it is therefore identical to the primary reader alone. On the tune split, no threshold raised accuracy, and escalating every page lowered accuracy from 98.75% to 97.92% at 1.7 times the cost, because the second reader is not stronger than the first. The primary's confidence is 1.0 on 214 of 240 instances, yet its two test errors carried its two lowest confidences, 0.90 and 0.95, both on one degraded page. With five errors across both splits, I cannot say whether that is a signal. A cascade needs a stronger second reader before the trigger matters.

Double-keying earned its cost on hallucinations. On its own, the verifier invented five values on out-of-distribution pages; for example, it read a utility bill's "Amount Due" as a claim total. Under double-keying, none of those values reached the output. The primary happened to be right on those pages, so in this sample the flags were review cost; had the roles been reversed, they would have been saved payouts. On total_amount, the payment field, the primary alone scored 97.5% [87.1–99.6] and the double-key pair scored 100% [90.8–100].

Of the test documents, 34 have an itemization and a stated total, and 12 are inconsistent by construction. The primary caught all 12 [75.8–100]. The verifier missed one, which is a claim that would have been paid. The models' arithmetic was right on every document, and every verdict failure traces to a misread digit on a degraded scan; line items were read correctly 91.2% of the time [77.0–97.0].

Several things are not established. A sample of 240 field-instances and 8 flags is small. This corpus has one complete run; three runs on the previous corpus moved accuracy by 0.4 points, so any single figure should be read as ±0.4. Calibration cannot be assessed when 239 of 240 predictions fall in one bin. The degraded stratum is the only one below 100% for the primary (95.8% [86.0–98.8]), and it is where double-keying's coverage drops most (93.8%, and 79.2% on out-of-distribution pages).

2.4 Monitoring in production

For each document, the pipeline already emits the disagreement rate between readers by field and by stratum, the adjudicator's ruling on each flagged item (which makes abstention precision a running measurement), the cost from usage metadata, latency and error rates, and the model version string. The following plan is proposed for Meridian to confirm.

  • Daily, the disagreement rate is compared with its baseline of 3.3% of fields. A rate above twice the baseline pages the on-call engineer, because either the input mix has moved or a model has changed.
  • Weekly, a 200-document sample is re-scored with this harness unchanged, using the adjudicators' final values as labels. Two percent of the agreed items are checked by a person, because two readers agreeing on a wrong value is the one failure the system cannot see on its own.
  • If the lower bound of accuracy on covered falls below 97% on the weekly sample, automatic payment stops until the cause is found.
  • The model name is an alias, so any change in the version string returned by the API triggers a re-run of the harness on the committed corpus before the next batch.

The throughput limit is account quota. The pipeline processes about 8 documents a minute from 1 to 8 workers and 12% fewer at 16, so 40,000 documents take about 83 hours of continuous running. The Batch API is the right mode for overnight bulk at half the price, but batches.create failed a precondition on this tier (F-011), so no batch cost is claimed.

2.5 Pilot gates

For the 500-document pilot, I would proceed with double-keying if the lower bound of accuracy on covered is at or above 97%, coverage is at or above 90% (a figure to be set against the exception queue's capacity), and at least one flag in three is a real error. If the last gate fails, the primary alone with a sampled audit is the honest alternative.
