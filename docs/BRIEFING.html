Context

Meridian is a composite partner profile built for this exercise: about 40,000 scanned claims documents a month; six payment-critical fields (claim id, policy number, claimant, provider, date of service, total amount); 97% field accuracy; under $0.02 a document; and flags instead of guesses, because a wrong payout costs far more than a review. I built a prototype extractor and an evaluation harness on a synthetic corpus of 80 documents, labels written first and pages rendered from them, so the failure distribution is my guess at theirs. Everything ran on the free tier, which forced one design change (1.3) and produced most of section 3.

1. Architecture

1.1 Flow

Labels (authored first, seeded) → rendered pages (five strata, scanner noise and JPEG loss on every page) → extractor (Gemini structured output against a response schema, one nullable value and one confidence per field) → response cache (every raw response, keyed on model, prompt version, schema and image bytes, committed) → harness (scores the cache offline, never calls the API).

Extraction and scoring are separate programs. Thresholds are chosen from cached responses, so sweeps cost no calls, tuning is reproducible, and the demo replays offline with identical numbers. Both programs recompute the cache key on read: a regenerated page scored against an old response would give plausible wrong numbers, so it is refused.

1.2 Configurations

  • primary_solo: one reader, gemini-3.5-flash-lite; abstain on low self-reported confidence.
  • verifier_solo: the second reader, gemini-3.1-flash-lite, on its own; same rule.
  • cascade: the primary reads; the page goes to the verifier when the primary's confidence is low.
  • double_key: both readers on every page; a field goes to review when their normalized values disagree. This automates the double-keying control Meridian's processors already run with people.

2. Evaluation

2.1 Definitions

  • Unit: the field-instance, one field on one document, because Meridian pays per field. Exact and normalized match are both reported and never merged.
  • Three error kinds, never pooled: wrong value (a wrong payout), missed field (a rekey), hallucinated field (a payment on a page that isn't a claim). Accuracy is never reported without coverage; abstention precision uses the recorded counterfactual for each flag.
  • Calibration in ten confidence bins with expected calibration error, flagged degenerate when fewer than two bins hold enough predictions to estimate from. Wilson 95% intervals on every proportion.
  • Configurations are compared paired on the same documents: McNemar's exact test on discordant instances, plus a bootstrap that resamples documents.
  • Reconciliation: does the itemisation sum to the stated total. This is the adjudication step under the transcription, where a processor loses money.

2.2 Protocol

80 documents in five strata (clean 24, ambiguous 16, degraded 16, incomplete 16, out-of-distribution 8), split 40 tune / 40 test before the first API call. Thresholds were swept on tune only. Test was scored once.

Cascade. Not shown separately: tuning set its escalation threshold to zero, so on test it is the primary alone. On tune, no threshold raised accuracy, and escalating every page lowered it from 98.75% to 97.92% at 1.7 times the cost, because the second reader isn't stronger than the first. The primary's confidence is 1.0 on 214 of 240 instances; its two test errors were its two lowest confidences (0.90 and 0.95, both on one degraded page), but with five errors across both splits I can't say whether that is signal. A cascade needs a stronger second reader before the trigger matters.

Double-keying. On its own, the verifier invented five values on out-of-distribution pages, for example a utility bill's "Amount Due" read as a claim total. Under double-keying none of them reached output. The primary happened to be right on those pages, so here the flags were review cost; with the roles reversed they would have been saved payouts. On total_amount: primary alone 97.5% [87.1–99.6], double-keyed 100% [90.8–100].

Reconciliation. 34 test documents have an itemisation and a stated total; 12 are inconsistent by construction. The primary caught all 12 [75.8–100]. The verifier missed one, a claim that would have been paid. The models' arithmetic was right on every document; every verdict failure traces to a misread digit on a degraded scan (line items read correctly 91.2% [77.0–97.0]).

Caveats. 240 field-instances and 8 flags are small numbers. This corpus has one complete run; three runs on the previous corpus moved accuracy 0.4 points, so read any single figure as ±0.4. Calibration can't be assessed with 239 of 240 predictions in one bin. The degraded stratum is the only one below 100% for the primary (95.8% [86.0–98.8]) and where double-keying's coverage drops most (93.8%; 79.2% on out-of-distribution pages).

2.4 Monitoring in production

Per document, the pipeline already emits reader disagreement by field and stratum, the adjudicator's ruling on each flagged item (abstention precision as a running number), cost from usage metadata, latency and error rates, and the model version string. What I would set up with Meridian, subject to their confirmation:

  • Daily: disagreement rate against its 3.3% baseline. Above twice baseline, page someone; the input mix moved or a model changed.
  • Weekly: re-score a 200-document sample with this harness unchanged, adjudicators' final values as labels. Human-check 2% of agreed items, since two readers agreeing on a wrong value is the failure the system can't see.
  • Kill switch: accuracy on covered (lower bound) below 97% on the weekly sample stops auto-pay until the cause is found.
  • Model version: the model name is an alias. A change in the returned version re-runs the harness on the committed corpus before the next batch.

The throughput limit is account quota: about 8 documents a minute from 1 to 8 workers and 12% slower at 16, so 40,000 documents is about 83 hours of continuous running. The Batch API is the right mode for overnight bulk at half the price, but batches.create failed a precondition on this tier (F-011), so I am not claiming a batch cost.

2.5 Pilot gates

For the 500-document run, proceed with double-keying if accuracy on covered (lower bound) is at or above 97%, coverage is at or above 90% (to be set against the exception queue's capacity), and at least one flag in three is a real error. If the last gate fails, the primary alone with a sampled audit is the honest alternative.
