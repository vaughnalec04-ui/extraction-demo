Context

Meridian is a composite partner profile I put together for this exercise. They receive about 40,000 scanned claims documents a month and need six payment-critical fields extracted: claim id, policy number, claimant, provider, date of service and total amount. Their stated requirements: 97% field accuracy, under $0.02 a document, and the system has to flag what it isn't sure of rather than guess, because a wrong payout costs far more than a review. I built a prototype extractor and an evaluation harness against a synthetic corpus of 80 documents. Labels were written first and each page rendered from its label, so no label depends on a model; the failure distribution is my guess at theirs, not theirs. Everything ran on the free tier, which forced one design change (1.3) and produced most of section 3.

1. Architecture

1.1 Flow

Labels (authored first, seeded) → rendered pages (five strata, scanner noise and JPEG loss on every page) → extractor (Gemini structured output against a response schema, one nullable value and one confidence per field) → response cache (every raw response, keyed on model, prompt version, schema and image bytes, committed to the repo) → harness (scores the cache offline, never calls the API).

Extraction and scoring are separate programs on purpose. Thresholds are chosen from cached responses, so sweeps cost no calls, tuning is reproducible against a fixed set of responses, and the demo replays offline with identical numbers. Both programs recompute the cache key on read, so a regenerated page can't be scored against an old response. That failure mode doesn't crash; it produces plausible wrong numbers, which is why it gets a check.

1.2 Configurations

Four, all resolved from the same cached calls.

  • primary_solo: one reader, gemini-3.5-flash-lite. Abstain on low self-reported confidence.
  • verifier_solo: the second reader, gemini-3.1-flash-lite, on its own. Same rule.
  • cascade: the primary reads; the page goes to the verifier when the primary's confidence is low. The standard cost saver.
  • double_key: both readers on every page; a field goes to review when their normalized values disagree. This is the automated version of the double-keying control Meridian's processors already run with people.

2. Evaluation

2.1 Definitions

  • Unit: the field-instance, one field on one document. Meridian pays per field.
  • Exact and normalized match are both reported and never merged. Normalization takes money to cents, dates to ISO, names to case- and punctuation-folded form with token order kept.
  • Three error kinds, never pooled, because they cost different things: wrong value (a wrong payout), missed field (a rekey), hallucinated field (a payment on a page that isn't a claim).
  • Accuracy is never reported without coverage; a system that abstains on everything scores 100%. Abstention precision uses the recorded counterfactual for each flag, meaning what would have gone out without it.
  • Calibration: ten confidence bins and expected calibration error, flagged degenerate when one bin holds everything. 95% Wilson intervals on every proportion, because n is small and the rates sit near 1.0, where the normal approximation breaks.
  • Configurations are compared paired, on the same documents: McNemar's exact test on discordant instances, plus a bootstrap that resamples documents, since six fields on one page share one scan.
  • Reconciliation: does the itemisation sum to the stated total. Field reading is transcription; this is the adjudication step under it, and it's where a processor actually loses money.

2.2 Protocol

80 documents in five strata (clean 24, ambiguous 16, degraded 16, incomplete 16, out-of-distribution 8), split 40 tune / 40 test before the first API call. Thresholds were swept on tune only. Test was scored once.

Cascade. Tuning set the escalation threshold to zero, so on test the cascade is just the primary. On tune, no threshold raised accuracy, and escalating every page lowered it from 98.75% to 97.92% at 1.7 times the cost, because the second reader isn't stronger than the first. The primary's confidence is 1.0 on 214 of 240 instances. Its two test errors were its two lowest confidences (0.90 and 0.95, both on one degraded page), but with five errors across both splits I can't say whether that is signal. What I can say is that a cascade needs a stronger second reader before the trigger matters.

Double-keying. On its own, the verifier invented five values on out-of-distribution pages, for example a utility bill's "Amount Due" read as a claim total. Under double-keying none of them reached output. The primary happened to be right on those pages, so here the flags were review cost; if the roles had been reversed they would have been saved payouts. On total_amount specifically: primary alone 97.5% [87.1–99.6], double-keyed 100% [90.8–100].

Reconciliation. 34 test documents have an itemisation and a stated total; 12 are inconsistent by construction. The primary caught all 12 [75.8–100]. The verifier missed one, a claim that would have been paid. The models' arithmetic was right on every document; every verdict failure traces to a misread digit on a degraded scan (line items read correctly 91.2% [77.0–97.0]).

Caveats. 240 field-instances and 8 flags are small numbers. This corpus has one complete run; three runs on the previous corpus moved accuracy 0.4 points, so read any single figure as ±0.4. Calibration can't be assessed with 239 of 240 predictions in one bin. The degraded stratum is the only one below 100% for the primary (95.8% [86.0–98.8]) and the one where double-keying's coverage drops most (93.8%, and 79.2% on out-of-distribution pages).

2.4 Monitoring in production

The pipeline already emits, per document: reader disagreement by field and stratum; the adjudicator's ruling on each flagged item, which turns abstention precision into a running number; cost from usage metadata; p50 and p95 latency with the 429 and 503 rate; and the model version string on each response. What I would set up with Meridian, subject to their confirmation:

  • Daily: disagreement rate against its baseline of 3.3% of fields. Above twice baseline, page someone; either the input mix moved or a model changed.
  • Weekly: re-score a 200-document sample with this harness unchanged, using adjudicators' final values as labels. Human-check 2% of agreed items, because two readers agreeing on a wrong value is the failure the system can't see on its own.
  • Kill switch: if accuracy on covered (lower bound) drops below 97% on the weekly sample, auto-pay stops and everything goes to the queue until the cause is found.
  • Model version: the model name is an alias. Any change in the returned version re-runs the harness on the committed corpus before the next batch.

Throughput is bound by quota, not by the client: about 8 documents a minute from 1 to 8 workers and 12% slower at 16, behind one shared rate gate. 40,000 documents is about 83 hours of continuous running with no headroom. The Batch API is the right mode for overnight bulk at half the price, but batches.create failed a precondition on this tier (F-011), so I am not claiming a batch cost.

2.5 Pilot gates

For the 500-document run, proceed with double-keying if: accuracy on covered, lower bound, is at or above 97%; coverage is at or above 90% (to be set against the exception queue's capacity); and at least one flag in three is a real error. If the last gate fails, the second reader is buying insurance the numbers don't show, and the primary alone with a sampled audit is the honest alternative.
